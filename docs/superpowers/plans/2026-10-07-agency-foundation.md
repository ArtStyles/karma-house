# Registro, aprobación, verificación y equipo de inmobiliarias Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Permitir solicitar una inmobiliaria desde el registro, separar su aprobación de la verificación concedida por KarmaHouse, mostrar el check verde y gestionar miembros con funciones acumuladas.

**Architecture:** Crear una solicitud privada a partir del alta de Auth y una agencia cuya aprobación habilita la primera membresía administrativa. La verificación usa solicitudes y concesiones privadas independientes, exclusivas del propietario de KarmaHouse. Las RPC comprueban aprobación, actor y membresía; un provider independiente limpia el contexto cuando cambia cuenta o agencia.

**Tech Stack:** Expo SDK 57, Supabase Auth/Postgres/Storage, TypeScript, `node:test` y `pg` existentes.

**Spec:** [Diseño](../specs/2026-10-07-agency-workspaces-design.md). Leer también el [índice y contratos comunes](2026-10-07-agency-workspaces.md).

## Global Constraints

- Una inmobiliaria debe esperar la confirmación del propietario de KarmaHouse antes de operar.
- La aprobación inicial no verifica la agencia; solicitar verificación tampoco permite publicar directamente. Solo KarmaHouse concede o revoca el sello.
- Conservar la verificación personal existente separada de la empresarial; ningún miembro hereda un sello personal de su agencia.
- El coordinador puede hacer todo lo que hace un gestor. El administrador puede hacer todo lo que hacen el gestor y el coordinador.
- Administrar una inmobiliaria no concede privilegios de plataforma ni acceso a otras agencias.
- Preservar registro y funciones personales; no almacenar contraseñas en borradores, solicitudes o logs.
- El módulo permanece desactivado por defecto; las pruebas locales lo habilitan solo en fixtures.

## Review Focus

1. Confirmación de correo en otro dispositivo: la solicitud continúa desde servidor; tarea 3.
2. Un registro repetido o una respuesta perdida: una sola solicitud y membresía; tarea 2.
3. Metadatos manipulados con `approved` o `admin`: ningún privilegio; tareas 1 y 2.
4. Una agencia pendiente intenta invitar, publicar o cerrar: denegación en servidor; tarea 2 y regresión de fase 4.
5. Cambiar cuenta o agencia con peticiones activas: ningún dato anterior se aplica; tarea 4.
6. Un administrador de agencia o un moderador normal intenta conceder el sello: denegación en servidor; tarea 2. Concesión directa y concesión tras solicitud comparten auditoría y control exclusivo del propietario.
